μBot Perception Architecture

A complete ROS stack for the 4-actuator μBot, built on one optimized forward gait γ*. Head sensors (camera, range, IMU) feed perception. A state estimator and a landmark SLAM node track where the robot is and build a map. A mission node sets goals, behaviour turns goals and perception into swimming primitives (forward, turn with bias voltage, backward with flipped phases), and a supervisor keeps the whole loop safe. The existing EM-PGPE training pipeline stays as it is and produces γ* offline.

Perception and steering

With the head swing minimized, each sensor is used at its own rate. A moving average over exactly one stroke period (1/f) removes whatever swing is left. There is only one steering input, the bias voltage b. So range and camera never set b themselves. They propose a desired heading ψ_ref or ask for BACKWARD, a priority arbiter picks one, and a single IMU heading controller turns ψ_ref into b.

Design notes

  • One writer for b. If range and camera each drove b, they would fight whenever an obstacle sits between the robot and the target. Sending everything through ψ_ref and one cascade avoids that.
  • Two independent collision triggers. Range TTC is accurate but only covers 5 beams. Camera looming TTC covers the whole image but needs texture. Either one can request BACKWARD.
  • Keep the 1/f average. Even a minimized head swing leaves some ripple at the stroke frequency. Averaging over exactly one period removes it with less lag than a general low-pass filter.
  • Use sim time everywhere. The camera slows Gazebo below real time. Stamps must come from /clock, or the Kalman filters get wrong time steps.
slam_node

SLAM

μBot swims in a plane at fixed depth, so SLAM only has to estimate x, y and heading. Its sensors are a 5-beam range fan, a small camera and an IMU, which rules out most off-the-shelf SLAM. The design that fits is landmark pose-graph SLAM on ArUco markers: markers on the tank walls give bearing and distance with a known identity, so matching observations to landmarks is free and loop closure happens whenever the robot sees a marker again. The range fan then fills in an occupancy grid using the optimized poses.

ApproachFit for μBotWhy
Landmark pose-graph SLAM (ArUco + GTSAM, or the fiducial_slam package)use thisWorks with a small camera and sparse range. Data association is free from marker IDs. Light enough to run alongside a slow Gazebo simulation.
2D laser SLAM (slam_toolbox, Cartographer, GMapping)noScan matching needs hundreds of beams per scan. Five beams don't constrain the pose.
Visual-inertial SLAM (ORB-SLAM3 mono-inertial, VINS-Mono, OpenVINS)laterWorks without markers, but needs a textured scene, more compute, and an IMU that measures gravity. mubot.world sets gravity to 0, so the simulated accelerometer never sees it and initialization fails. Fix: turn world gravity on and switch it off per link in the URDF.

Odometry from the gait

μBot has no wheels, so odometry comes from a speed model. Run the fixed policy at several amplitude scales k and both directions, read the true speed from /mubot/odom, and fit v = g(k, mode) as a lookup table. The EKF fuses that speed with the IMU heading. Expect position drift of several percent of distance swum. SLAM corrects it every time a marker comes back into view.

Turning also changes forward speed. Include bias b in the lookup table if turns are frequent.

Setting up the tank

  • Put ArUco 4×4 markers on the walls, about 20 cm apart, so at least one is usually in view.
  • At 320 × 240 pixels, a 4 cm marker is detectable to roughly 0.8 m. At 160 × 120 the range halves, which is why the camera resolution was raised.
  • Add a few markers on obstacles too. They become landmarks and the map shows them.
  • Give walls and obstacles textures as well, so camera looming still works between markers.

Timing

The physics and the waveform run at 4 kHz inside Gazebo. Each sensor is processed at its own rate. The heading cascade runs at 20 Hz, which is already faster than a bias change can act. SLAM runs on keyframes rather than a clock, so its cost scales with distance swum, not with time.

The watchdog timeout (200 ms) is ten command periods. One late message never trips it, but a crashed node does.

Build order

  1. Safe plumbing. Actuator plugin with ROS subscriber, bias, watchdog and e-stop; TF from robot_state_publisher; teleop. Drive the primitives by hand.
  2. Heading hold. Measure the bias-step response, then tune the heading cascade.
  3. Speed model and EKF. Fit v = g(k, b, mode) from ground truth, run the EKF, and check drift against /mubot/odom.
  4. Target seeking. Camera, blob detection, visual servoing.
  5. Obstacle avoidance. Range TTC, VFH+, arbiter, camera looming.
  6. SLAM. ArUco landmarks, pose graph, then the occupancy grid. Validate against ground truth.
  7. Missions. ReturnHome first (needs only the pose), then Explore (needs the grid), then SeekTarget with search.

Risks to check early

  • About 0.2° of steady bend per volt of bias per joint at K = 3.75e-3. Measure turn rate before tuning anything that steers.
  • Bias eats amplitude headroom under the ±15 V clip.
  • The camera now runs at 320 × 240 for marker range, which slows Gazebo further. Measure the real-time factor early.
  • Gait odometry drifts. If markers are out of view for long stretches, the pose and the map degrade together.
  • World gravity is 0, so the simulated IMU never measures gravity. Fine for the EKF and landmark SLAM; blocks visual-inertial SLAM.
  • Infrared range sensors reach only a few centimetres underwater. A real range fan means small ultrasonic sonar.
  • The repo is ROS 1 and Gazebo Classic, both past end of life. Porting to ROS 2 before building this stack is cheaper than after.
