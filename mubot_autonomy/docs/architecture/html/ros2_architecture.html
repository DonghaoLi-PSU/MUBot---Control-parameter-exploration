μBot ROS 2 Architecture

The same robot, perception, SLAM and control design as the ROS 1 page, rebuilt on ROS 2 and modern Gazebo. The biggest structural change is that the simulator no longer speaks ROS. Gazebo runs its own message bus (gz-transport), and a bridge layer connects it to the ROS 2 graph. The custom hydrodynamics and actuator code become Gazebo system plugins, and the EM-PGPE training loop drops its CSV files and runs rollouts in parallel.

Porting the actuator plugin

A gz sim system is a class that implements one or more interfaces. Configure runs once when the model loads. PreUpdate runs every physics step before the solver, which is where forces and torques go. The hydro system follows the same pattern, with link velocities in and AddWorldWrench out.

The command callback runs on a gz-transport thread, so it only copies the message under a mutex. The watchdog uses sim time, read inside PreUpdate, so it behaves the same whether the simulation runs faster or slower than real time.

Joint names come from the SDF instead of being hardcoded, so the same plugin works for NoA = 2, 4 or 6.

class ActuatorSystem : public gz::sim::System,
                       public gz::sim::ISystemConfigure,
                       public gz::sim::ISystemPreUpdate {
 public:
  void Configure(const gz::sim::Entity &entity,
                 const std::shared_ptr<const sdf::Element> &sdf,
                 gz::sim::EntityComponentManager &ecm,
                 gz::sim::EventManager &) override {
    gz::sim::Model model(entity);
    for (auto e = sdf->FindElement("joint_name"); e;
         e = e->GetNextElement("joint_name")) {
      gz::sim::Joint j(model.JointByName(ecm, e->Get<std::string>()));
      j.EnablePositionCheck(ecm, true);
      j.EnableVelocityCheck(ecm, true);
      joints_.push_back(j);
    }
    node_.Subscribe("/model/mubot/gait_cmd",
                    &ActuatorSystem::OnCmd, this);
  }

  void PreUpdate(const gz::sim::UpdateInfo &info,
                 gz::sim::EntityComponentManager &ecm) override {
    if (info.paused) return;
    const double t = std::chrono::duration<double>(info.simTime).count();
    std::lock_guard<std::mutex> lock(mutex_);
    if (fresh_) { lastCmd_ = t; fresh_ = false; }
    const bool stale = estop_ || (t - lastCmd_ > 0.2);
    for (size_t i = 0; i < joints_.size(); ++i) {
      const double q  = joints_[i].Position(ecm)->at(0);
      const double qd = joints_[i].Velocity(ecm)->at(0);
      const double E  = stale ? 0.0 : Voltage(i, t);   // e·sin(...)+b, clipped
      joints_[i].SetForce(ecm, {MotorTorque(E, qd) - Stiffness(i) * q});
    }
  }
  // OnCmd, Voltage, MotorTorque, Stiffness, members omitted
};

GZ_ADD_PLUGIN(ActuatorSystem, gz::sim::System,
              ActuatorSystem::ISystemConfigure,
              ActuatorSystem::ISystemPreUpdate)

Training without the CSV file bus

Training doesn't need the ROS graph at all. The trainer can talk to the workers through gz-transport directly from Python. Only the deploy stack needs ROS 2.

Optional: Nav2 for missions

Nav2 is worth it when missions need path planning around a mapped tank: costmaps from /mubot/map, behavior trees in place of a hand-written mission node, and recovery behaviours. Two limits to plan for. μBot can't hold position (it drifts when the gait stops), so goal tolerances must be loose. And its minimum useful speed is well above zero, so set the controller's minimum velocity accordingly. The reactive arbiter from the ROS 1 design stays in place for collision safety either way.

Migration order

  1. Freeze a baseline. On ROS 1, record the forward speed of the paper's optimized gaits for a few cases. These are the numbers the port must match.
  2. Workspace, interfaces, description. Convert the URDF to xacro with NoA as an argument.
  3. Port the two systems. Run the frozen gaits open-loop in gz sim and compare speed against the baseline. Fix differences here, before anything depends on the physics.
  4. Training workers. Port the rollout loop to Fig. 2 and re-train one case. The optimized speed should land near the paper's value.
  5. Sensors and bridge. Add the sensors, bridge.yaml and the command bridge. Check every topic in RViz.
  6. Deploy stack. Same order as the ROS 1 plan: heading hold, speed model and EKF, target seeking, avoidance, SLAM, missions.
  7. Nav2, only if the missions need planning.

Risks

  • Physics engine change. ODE to DART can change contact-free multibody dynamics through solver and joint-damping differences. Step 3 above exists for this.
  • 4 kHz physics plus rendering. Camera and gpu_lidar rendering at this step size is slow. Keep sensor rates low, and keep training workers sensor-free.
  • Headless rendering needs a GPU. CPU-only machines and many CI runners can't render camera or gpu_lidar data.
  • Custom messages don't bridge automatically. Anything beyond the standard mappings needs a small bridge node like mubot_gz_cmd_bridge.
  • Zero gravity. Still blocks visual-inertial SLAM. Same fix as before: world gravity on, per-link gravity off.
  • Sim time everywhere. One node without use_sim_time will misbehave silently, especially the watchdog and the Kalman filters.
